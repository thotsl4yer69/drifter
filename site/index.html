THE PROBLEM

Intermittent faults don't wait for a scanner.

Most diagnostic sessions begin after the symptom has already stopped. DRIFTER is built around the opposite assumption: preserve the window first, investigate second.

It runs as a dedicated node in the vehicle rather than depending on a phone being connected at the exact moment something goes wrong.

02

INCIDENT BLACK BOX

Keep the window around the event.

A bounded rolling buffer preserves evidence around automatic or manual incident capture. Sequencing shows what changed first; it does not pretend correlation proves root cause.

THE SYSTEM

A dedicated vehicle node, not another dashboard skin.

Vehicle data enters through the supported transport, moves through local services and becomes usable evidence at the touchscreen, logger and diagnostic layers.

INPUT Vehicle / OBD-II

ELM327 / legacy OBD paths or SocketCAN-oriented integration where appropriate.

CORE DRIFTER VIM

Raspberry Pi Linux node with MQTT service communication, local rules and logging.

OUTPUT Evidence / UI

Touchscreen state, incident bundles, drive logs, alerts and post-drive analysis.

01

Transport-aware

Adapter reachability, ECU response and live PID flow are separate states rather than one vague “connected” indicator.

02

Local-first

The core telemetry and evidence path runs on the node. Cloud access is not required for the core loop.

03

Touchscreen-first

Normal vehicle onboarding and recovery are designed to happen in FIELD OPS without a terminal.

04

Conservative updates

The updater is designed to defer while vehicle telemetry indicates the car is active and roll back a failed deployment.

05

Profile-driven

Vehicle identity, supported PIDs and diagnostic context can vary by validated vehicle profile.

06

Evidence-led

Measured sequencing and correlations are retained as evidence, not promoted as automatic proof of causation.

04

FIELD PROOF

Built on hardware. Still earning the green light.

DRIFTER is a substantial hardware-integrated prototype under active hardening. These are the acceptance gates that matter before a paid hardware release.

CURRENT GATE REFERENCE / JAGUAR X-TYPE

Primary vehicle acceptance

The 2004 Jaguar X-Type remains the reference platform until repeatability is recorded on the intended in-car hardware.

  • 10/10 cold starts from the intended vehicle power source
  • 30-minute RPM / coolant / speed / voltage telemetry session
  • ELM327 unplug / replug recovery or explicit actionable state
  • Display recovery without a full power cycle when Linux remains alive
  • Incident capture and field evidence preserved after a fault

COMPATIBILITY LANGUAGE

Targets standards-based OBD-II vehicles.

Actual capability depends on the vehicle protocol, attached adapter and PIDs the ECU supports. New combinations are promoted as tested only after real evidence.
